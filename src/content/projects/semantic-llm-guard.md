## Project goal

**semantic-llm-guard** is a semantic firewall for detecting *prompt
injection* and *jailbreak* attacks, aiming to protect a local LLM
(Qwen3-8B via Ollama) from malicious inputs before they reach the model.

The core approach uses **BGE-M3 embeddings** (`BAAI/bge-m3`) to
semantically represent each input prompt and compare it, via cosine
similarity, against a labeled corpus of known attack examples and
legitimate usage. This **semantic** detection approach is benchmarked
against a traditional **regex-based filtering** approach, allowing an
evaluation of the gains and limitations of each method — including the
BGE-M3's ability to generalize across languages (e.g., detecting in
Portuguese an attack originally described in English).

## Why Semantic Detection? (and why regex still matters)

Regex and keyword matching remain a common first line of defense against
prompt injection in production systems: they are fast, deterministic, and
cheap to run, since patterns are evaluated locally without needing a model
call. Guardrail architectures generally still rely on this kind of
pattern/schema matching for format validation — checking that an output
conforms to an expected structure is a case where a deterministic check is
the right tool, even in systems that otherwise use semantic layers for more
open-ended categories such as jailbreak/injection detection, PII handling,
toxicity, topic policy, and groundedness.

This project does not argue that regex should be replaced. Its goal is to
quantify a specific, well-known gap that keyword-based filtering leaves
open: paraphrased attacks that avoid known trigger phrases. The evaluation
in this repository (`results/evaluation_report.json`) offers direct
evidence of that gap:

- The regex baseline detected 0 of 8 paraphrased/subtle attacks in the test
  set, and produced 2 false positives on benign examples containing trigger
  words ("system administrator", "developer mode") used in an entirely
  harmless context.
- The semantic detector (BGE-M3) detected 4 of the same 8 paraphrased
  attacks, with 0 false positives, reaching an F1 score of 0.833 versus
  0.545 for the regex baseline.

The practical takeaway is not "replace regex with embeddings," but
defense-in-depth: a fast regex filter as a first line of defense against
obvious, known attack patterns, followed by a semantic layer that catches
paraphrases and subtler attempts the regex layer misses. This mirrors the
broader guidance from frameworks like the NIST AI Risk Management Framework
and the OWASP Top 10 for LLM Applications, both of which recommend
combining multiple, independent layers of defense rather than relying on
any single detection mechanism (see [References](#references)).

## Hardware Requirements

The semantic detector (BGE-M3) runs on CPU by default and works on any
machine. The local LLM (Qwen3-8B via Ollama) is the resource-heavy part;
`config.yaml` lets you swap it for a smaller variant if your hardware is
limited.

| Scenario | Hardware | Notes |
|---|---|---|
| Minimum | CPU only, no GPU | Works, but Qwen3-8B generation is slow. Set `llm.model` in `config.yaml` to `qwen3:4b` or `qwen3:1.7b` for usable latency. |
| Recommended | GPU with 6GB+ VRAM (e.g. RTX 3050) | Qwen3-8B runs mostly on GPU; expect some CPU offload with the default context size — see the VRAM contention note below. |
| Ideal | GPU with 8GB+ VRAM | Qwen3-8B fits fully on GPU with room for a larger context window. |

To use a smaller model, edit `config.yaml`:

```yaml
llm:
  model: qwen3:4b   # or qwen3:1.7b for very limited hardware
```

Then pull it once with Ollama: `ollama pull qwen3:4b`.

## Quick Start with Docker

An alternative to the manual setup above (venv + local Python + local
Ollama install) — useful if you'd rather not configure the environment
from scratch. Requires [Docker](https://docs.docker.com/get-docker/) and
the Docker Compose plugin.

```bash
# 1. Start the Ollama service
docker compose up -d ollama

# 2. Pull the model inside the container (one-time)
docker compose exec ollama ollama pull qwen3:8b

# 3. Run the demo
docker compose run semantic-firewall python src/demo_scenarios.py

# 4. Run the evaluation
docker compose run semantic-firewall python src/evaluate.py
```

`docker-compose.yml` runs two services: `ollama` (official image, with a
named volume so pulled models persist across restarts) and
`semantic-firewall` (built from the project's `Dockerfile`, CPU-only torch
since BGE-M3 runs on CPU by default). The `semantic-firewall` container
talks to `ollama` over the Compose network via the `OLLAMA_HOST` env var
(see `OLLAMA_HOST` in `src/pipeline.py`), and `./results` is mounted into
the container so logs, embeddings, and charts persist on the host. GPU
acceleration for the `ollama` service is optional and commented out in
`docker-compose.yml` — it requires the [NVIDIA Container
Toolkit](https://github.com/NVIDIA/nvidia-container-toolkit) installed on
the host.

## Pipeline integration

The semantic detector sits in front of the local LLM as a triage step: every
user input is classified before it is allowed to reach Qwen3-8B. Requests
flagged as an attack are blocked immediately and never sent to the model.

```
user input
    |
    v
BGE-M3 embedding
    |
    v
similarity check (vs. labeled corpus)
    |
    +-- flagged=True  --> [BLOCKED]  (logged, no request sent to the model)
    |
    +-- flagged=False --> forwarded to Qwen3-8B via Ollama --> response
```

![Architecture diagram of the pipeline: user input flows through BGE-M3 embedding and a similarity check, then branches to either a blocked path or forwarded to Qwen3-8B, both ending in the pipeline log](https://raw.githubusercontent.com/lalabohm/semantic-llm-guard/main/results/pipeline_architecture.png)

*Every request is logged regardless of outcome — blocked requests are
logged without ever reaching Qwen3-8B.*

Each request processed by the pipeline (`src/pipeline.py`) is logged as a
JSON line in `results/pipeline_log.jsonl`, including the decision, the
matched category and similarity score, and the latency of each stage
(semantic triage vs. model response).

### A note on GPU contention (6GB VRAM)

On a 6GB GPU (RTX 3050), running BGE-M3 and Qwen3-8B on the GPU at the same
time causes VRAM contention: Ollama doesn't get enough free memory to fit
Qwen3-8B and falls back to a slow CPU/GPU split, turning a normal response
into a multi-minute wait. Three changes in `src/pipeline.py` and
`src/semantic_detector.py` address this:

- **BGE-M3 runs on CPU by default.** It only needs ~90ms per request after
  warmup, which is fast enough for a triage step, and it means it never
  competes with Qwen3-8B for VRAM in the first place.
- **A smaller context window** (`num_ctx=2048`) reduces Qwen3-8B's VRAM
  footprint, since even alone it doesn't fully fit in this card's ~5.67GB
  of usable VRAM at the default 4096-token context.
- **Thinking mode is disabled** (`think=False`) for these straightforward
  informational prompts, avoiding a large number of hidden reasoning
  tokens that roughly doubled generation time.

Combined, these took the benign end-to-end scenario in the demo below from
~254s to ~51s. `pipeline.py` also logs VRAM usage (`gpu_release` field in
`pipeline_log.jsonl`) around a defensive GPU-memory release step, so any
regression here is visible directly in the log.

### Running the demo

```
python src/demo_scenarios.py
```

This runs 3 representative scenarios end-to-end (a classic prompt
injection, a paraphrased/subtle attack, and a legitimate benign request)
and prints the decision, category, similarity score, and per-stage latency
for each — the response from Qwen3-8B is only shown for the request that
is allowed through.
